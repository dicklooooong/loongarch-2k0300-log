## 四、现象 vs 预期（嵌入式排错的核心）

| # | 我预期发生 | 实际发生（贴原文/关键行） | 说明 |
| --- | --- | --- | --- |
| 1 | `git --version` 打印版本号 | `无法将"git"项识别为 cmdlet、函数、脚本文件或可运行程序的名称` | 不是 PATH 问题，是根本没装；用 `Test-Path` 交叉确认 |
| 2 | `winget install --id Git.Git` 能装上 Git | 无任何输出，退出码 1；`winget --version` 同样无输出 | `winget.exe` 是 **0 字节**的应用执行别名，非交互进程调用起不来 |
| 3 | `curl https://github.com` 返回 200 | `curl: (35) schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`，http_code=000 | 换 bing.com / microsoft.com **同样报错** ⇒ 是环境出网策略，不是 GitHub 的问题 |

> 第 3 条是关键判断：如果只在 github.com 上失败，会去查代理和 DNS；发现**所有**站点都失败，才能立刻改方向。

## 五、关键收获（≤3 条）

1. **收获**：先做环境事实核查，再谈方案。｜ 为什么重要：省掉了"以为没配 PATH"的错误排查方向。
2. **收获**："命令不存在"要分「没安装」和「不在 PATH」两种，用 `Get-Command` + `Test-Path` 一次问清。｜ 为什么重要：两种原因的修法完全不同。
3. **收获**：判断网络问题要看**多站点对照**，单点失败无法区分是站点还是本机。｜ 为什么重要：这是嵌入式里同样适用的排查范式（换线/换板对照）。
