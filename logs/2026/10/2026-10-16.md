## 四、现象 vs 预期（嵌入式排错的核心）

| # | 我预期发生 | 实际发生（贴原文/关键行） | 说明 |
| --- | --- | --- | --- |
| 1 | `git --version` 打印版本号 | `无法将"git"项识别为 cmdlet、函数、脚本文件或可运行程序的名称` | 不是 PATH 问题，是根本没装；用 `Test-Path` 交叉确认 |
| 2 | `winget install --id Git.Git` 能装上 Git | 无任何输出，退出码 1；`winget --version` 同样无输出 | `winget.exe` 是 **0 字节**的应用执行别名，非交互进程调用起不来 |
| 3 | `curl https://github.com` 返回 200 | `curl: (35) schannel: AcquireCredentialsHandle failed: SEC_E_NO_CREDENTIALS (0x8009030e)`，http_code=000 | 换 bing.com / microsoft.com **同样报错** ⇒ 是环境出网策略，不是 GitHub 的问题 |
| 4 | 提到完整权限后应该就能下载了 | `schannel: next InitializeSecurityContext failed: CRYPT_E_NO_REVOCATION_CHECK (0x80092012)`；同一次测试里 `git-scm.com` 却返回 **200** | 凭据这次拿到了，卡在**证书吊销检查**：沙箱内查不到 OCSP/CRL。用 `http.schannelCheckRevoke=false` 绕过 |
| 5 | `git rebase --continue` 能正常收尾 | `true (35400) ... *** fatal error - couldn't create signal pipe, Win32 error 5`，随后 `there was a problem with the editor` | git 会拉起 **MSYS 的 sh.exe** 来执行编辑器，而沙箱禁止命名管道 ⇒ 任何需要编辑器的 git 操作都会失败 |
| 6 | 推送应被拒绝（远程已有提交） | `ls-remote` 显示 `refs/heads/main` 已存在（`e92fa3c`） | 若直接 push 会 non-fast-forward；先 fetch 并整合历史才是正解 |
| 7 | 没有 PAT 就推不上去 | `git push` 直接成功，未出现任何登录提示 | 授权其实可用：完整权限下 GCM 读到了 Windows 凭据管理器里已存的 GitHub 凭据 |

> 第 3～4 条连起来看是关键判断：**同一个操作在不同权限层级下表现完全不同**。
> 单站点失败 → 查站点；全站点失败 → 查本机策略；受限 shell 失败而完整权限成功 → 查沙箱/权限层。

## 五、关键收获（≤3 条）

1. **收获**：先做环境事实核查，再谈方案。｜ 为什么重要：省掉了"以为没配 PATH"的错误排查方向，也第一时间定位到工具缺失。
2. **收获**："命令不存在"要分「没安装」和「不在 PATH」两种，用 `Get-Command` + `Test-Path` 一次问清。｜ 为什么重要：两种原因的修法完全不同。
3. **收获**：排错第一步是判断"问题在哪一层"，对照实验是最便宜的定位手段——多站点对照定位网络，多权限对照定位沙箱，多版本对照定位工具链。｜ 为什么重要：嵌入式里同样是这套方法：换线、换板、换电源做对照，比盯着报错猜快得多。
