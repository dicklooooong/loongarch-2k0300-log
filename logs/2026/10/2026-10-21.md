## 三、做了什么（事实）

1. 先确认现象：`lsusb` 只有三个根集线器、`/dev` 下只有 `fb0`、`/proc/devices` 里**没有 `81 video4linux`**、`/sys/class/video4linux` 不存在
2. 判定：不是摄像头、不是网络，是**内核没有 V4L2/UVC**——所以连设备节点都不会被创建
3. 备份当前内核 `/boot/vmlinuz` → `/boot/vmlinuz.bak-20261021`（md5 `14b5cd6f75cce83e5c322c311a5d452c`），并在 Windows 另存了一份
4. 上传 10/17 编的 `linux-4.19-202506/vmlinuz`（md5 `ef62fe1368d114b713d667bd97e5955a`）到板卡 `/tmp`，校验一致后写入 `/boot/vmlinuz`，`sync`，重启
5. **软重启后整条网段失联**：主机「以太网」变 `Media disconnected`，虚拟机 `.150`、板卡 `.140` 全部 timeout，等 2 分钟不恢复 → **断电重上电**后全部回来
6. 验证新内核：`/proc/devices` 出现 `81 video4linux`；`/sys/class/video4linux` 出现 `video0`/`video1`；`kallsyms` 里有 `uvc_probe`、`uvc_register_video_device`
7. 插上摄像头：`lsusb` 认出 `0bda:3835 USB Camera`，`/dev/video0` 出现
8. 改例程 `E08_02_tcp_client_uvc_rgb_demo`：`SERVER_IP` → `192.168.137.1`、`build.sh` 的 `REMOTE_IP` → `192.168.137.140`，`./build.sh` 编译 + 上传成功
9. 写 Windows 端接收端 `viewer.py`：解析 seekfree_assistant 图像协议，用 **Tkinter + PIL** 显示
10. 首帧是"大块错色 + 彩色雪花" → 定位为**字节序被交换了两次**（例程发前交换一次、接收端又按标准 RGB565 读），接收端再交换一次后颜色正常
11. 帧率调优：180 → 请求 90（实际 120）→ 请求 60（还是 120）→ 交叉编译 `v4l2enum.c` 上板枚举，确认**只有 120/180 两档** → 把 `UVC_FPS` 明确写成 120
12. 板端改独立进程：`setsid nohup ./E08_02... > /tmp/cam.log 2>&1 < /dev/null &` → `PPID=1`、`SID` 自己、`TTY=?`，SSH 断开也不影响
13. Windows 端做 `启动接收端.cmd`：第一版双击无效，改成 **CRLF 换行 + 纯 ASCII 内容** 后可用

## 五、关键收获（≤3 条）

1. **收获**：判断"驱动在不在"，看 `/proc/devices`（主设备号）和 `/proc/kallsyms`，**不要只看有没有 `.ko` 文件**。这种情况驱动是 `=y` 编进内核的，`find /lib/modules -name "*uvc*"` 一条都搜不到，但功能是有的。｜为什么重要：我一开始差点被"没有 ko 文件"带偏，去想办法 modprobe（板子上连 `modprobe` 命令都没有）。
2. **收获**：UVC 的帧率是**离散档位**，`cap.set(FPS, x)` 只是"就近请求"且不报错；要确认真实值必须回读 `cap.get(FPS)`，最靠谱是直接 `VIDIOC_ENUM_FRAMEINTERVALS` 枚举。｜为什么重要：写 60 却跑 120 这种"静默降级"极容易让人误判功耗/带宽的账。
3. **收获**：**软重启不等于重启**。这块板子 `reboot` 之后网络起不来，必须断电再上电。｜为什么重要：以后刷内核/改设备树，一律 `sync` + 断电，不要相信 `reboot`，也别在重启后立刻判定"刷坏了"。

### A、任务是什么

### B、技术路线（按龙邱 TinyClassifier 教程走）

```
PC：304 张数据集 → train_tiny_classifier.py（PyTorch）→ ONNX
```

**与教程的关键偏离**：不走"板卡篇"那套（解压 `ncnn-lib.tar.gz` + `ldconfig`），改成**静态链接库里自带的 `libncnn.a`**。原因见 D-1。

### C、做了什么（事实）

1. 读两份手册 + 摸清数据集结构：`武器104 / 物资104 / 载具96` 共 304 张，目录是"类别/子类/*.jpg"三层
2. 新建独立工程 `ncnn_cls/`（与 `project/` 平级），写板端推理程序，支持**摄像头模式**和**单张图片模式**
3. 踩了三个坑（见 D）
4. 真实评测：从 304 张里每类等距抽 20 张（共 60 张）→ **作者原模型 85.0%**
5. 混淆矩阵暴露短板：supplies 95% / vehicle 100% / **weapon 60%**，9 个错里 8 个是武器
6. 把这 60 张 MD5 去重后，用剩下 244 张重训一版（`width_mult` 0.6→1.0，参数 4323→10715）→ 干净图 81.7%，反而更差
7. **劣化实验**：把 60 张图模拟成"摄像头拍出来的样子"（旋转 ±6° → 缩到 160×120 → 高斯模糊 → 亮度/对比度扰动 → JPEG q45~70）
8. 结论：**容量不是瓶颈，数据域才是**

### E、关键收获（3 条）

1. **收获**：Linux 板子上"部署"不是"烧录"。scp 拷过去 + `./run` 就行，断电重启文件还在（只是不会自启）。只有内核和系统镜像才叫刷写。｜为什么重要：第一次接触的人会一直在找"下载器/烧录工具"。
2. **收获**：**评测必须控制变量**。同一批 60 张图、留出集不参与训练、MD5 去重——只有这样才能谈 A/B。否则"参数翻倍却更差"这种现象根本解释不清。｜为什么重要：这次正是靠这个，才发现作者 85% 里可能有数据泄漏。
3. **收获**：**数据域差异比模型容量更致命**。白底产品图 → 摄像头实拍，纯净度一降，作者模型掉 8.3 个点；而重训那版因为容量大反而抗劣化（81.7→85.0）。｜为什么重要：后面所有工作的重心应该放在"采自己拍的图"，而不是继续加参数。

### F、使用方法（写给明天忘了的自己）

完整手册在工作区的 `ncnn_cls/README.md`，这里只记最短路径。

**① 板子上跑（三条命令）**

```bash
ssh root@192.168.137.140
cd /home/root

```

**② 输出怎么读**

```

        三类得分: supplies=0.10 vehicle=0.03 weapon=0.87
[保持] weapon  conf=0.86  (10.4 ms)
```

- `[变化]` = 类别刚变（附三类得分）；`[保持]` = 同类，每 20 帧报一次
- `conf > 0.85` 可信；`0.6~0.85` 犹豫；`< 0.6` 基本是瞎猜
- 只有三类，**对着墙也会硬选一个**，这是正常的
- `Ctrl + C` 退出

**③ 三个参数是什么**

```
./ncnn_cls  <param模型结构>  <bin模型权重>  <labels类别名>  [可选:图片]
```

`labels.txt` 现在三行：`supplies / vehicle / weapon`（顺序必须和模型输出对应）

**④ 单张图片模式（调试用，跑一张就退）**

```bash
scp -O 图.jpg root@192.168.137.140:/home/root/      # 虚拟机上

```

**⑤ 换模型**：改前两个参数路径即可。模型必须先用 pnnx 从 ONNX 转：

